# Architecture

<Lead>
  Hookbeam is two services in one repository. The control plane faces people and senders; the data plane owns every
  message and does every delivery. Each has its own database, they talk through one gRPC contract and through events, and
  neither reads the other's tables.
</Lead>

<ArchitectureExplorer />

## Two planes

The split follows the two very different jobs the system has.

The **control plane** (`api/`) is the public face. It serves the REST API and the console's sessions, hosts identity
through goauth, holds API keys and roles, decides who may do what, and keeps the projections and notifications people
read. Its traffic is people and API calls: short requests, bursty, latency-sensitive.

The **data plane** (`delivery/`) is the delivery engine. It owns applications, endpoints, encrypted signing secrets,
messages with their exact bytes, deliveries and attempts. Its worker makes outbound HTTP requests to destinations
chosen by customers, which is the riskiest thing the system does, and it holds the payloads, which are the most
sensitive data. It is reachable only from the control plane, over mutual TLS.

Splitting them buys three things. The delivery engine's load and failures stay out of the request path that people
and senders use. Each plane has its own schema and migrations, so each can change without coordinating a shared
database. And the boundary is already a network contract, so either plane can later scale, deploy or be isolated on its
own. The cost is a second database, a gRPC hop on every delivery operation, and data that is copied rather than joined.
Both planes stay in one Go module and one repository, which keeps the contract and its callers changing in the same
commit.

## The contract between them

The control plane calls the data plane through the service defined in
<Source path="contracts/proto/hookbeam/delivery/v1/delivery.proto" />. Three rules make the boundary safe.

- **Mutual TLS both ways.** Both sides present certificates from one CA. Plaintext exists only for local development,
  and staging and production configurations refuse it.
- **The workspace is metadata, never a field.** The control plane derives the workspace from the caller's session or
  key and sends it, with the acting user and the request id, as call metadata. The data plane's interceptor rejects a
  call without it, and every repository read filters by it, so an id from another workspace is not found rather than
  forbidden: the response never confirms that it exists.
- **Errors cross as statuses.** Validation errors carry their fields, backpressure carries its `Retry-After`, and a data
  plane that does not answer becomes `503` with `Retry-After: 5` for the caller. Nothing is buffered in the control
  plane: an event that cannot be committed is not accepted.

## Processes

| Process | Runs | Scales by |
|---|---|---|
| `api/cmd/api` | The public HTTP API and goauth's routes under `/v1/auth` | Replicas behind the edge; it keeps no state between requests |
| `api/cmd/worker` | Relays the control plane's outbox; handles delivery state, health and email events | Replicas on one queue; each event is handled once by its id |
| `delivery/cmd/server` | The gRPC service: acceptance, configuration, every read | Replicas; it keeps no state between calls |
| `delivery/cmd/worker` | Claims and sends deliveries, sweeps expired leases, applies retention, relays the data plane's outbox | Replicas; claims are serialized by one lock, attempts run in parallel, ten at a time per replica by default |

Every process exits cleanly on `SIGTERM`: servers drain in-flight requests, consumers finish the message in hand, and
the delivery worker waits for the attempts it already started so that what was sent is recorded.

## Events between the planes

Anything that must happen after a transaction commits is written to that transaction's outbox and published later by
the relay. Both planes publish to one topic; each worker reads its own queue, filtered by event type.

| Event | From | To | Why |
|---|---|---|---|
| `delivery.due` | Data plane | Delivery worker | Wake up and claim now; the delivery itself is already in Postgres |
| `delivery.succeeded`, `.failed`, `.cancelled`, `.retry_scheduled` | Data plane | Control plane worker | Project each endpoint's recent health for the API and the console |
| `endpoint.health_changed` | Data plane | Control plane worker | Notify owners and admins when an endpoint fails repeatedly, and when it recovers |
| `notification.email_requested` | Control plane | Control plane worker | Send one alert email, outside the transaction that stored the notice |

The queue is never the source of truth. Losing a wake-up delays a delivery until the next claim tick; losing a state
event leaves a projection behind until the next one arrives; neither loses a delivery.

## Identity

Identity is [goauth](https://github.com/bete7512/goauth), mounted at `/v1/auth`: sign-up, login, refresh, verification,
password reset, Google sign-in, and organizations, which are Hookbeam's workspaces. Access tokens are ES256 JWTs with a
key id, published at `/v1/auth/.well-known/jwks.json`. The control plane validates every token online against the
user's current state in goauth, not only its signature. Hookbeam never writes SQL against goauth's tables; it
reads memberships and contacts through goauth's own storage interfaces.

## One origin

In front of both sits one origin: `/v1/*` and `/openapi.json` go to the control plane, everything else to the console
and these docs. The console's session cookie is therefore first-party, and the console never needs to know where the
API runs. Because cookies ride along on cross-site requests, the control plane refuses any state-changing request that
carries the session cookie but names no allowed origin.

## What is shared, and what is not

The two planes share libraries, not data. Everything under `pkg/` is domain-free: the outbox transport, gRPC plumbing,
the SSRF-safe HTTP client, Standard Webhooks signing, encryption, telemetry, the recurring-job runner. A lint rule stops
`pkg/` from importing either plane, and neither plane imports the other: the control plane reaches the data plane only
through the generated client in `contracts/`.
